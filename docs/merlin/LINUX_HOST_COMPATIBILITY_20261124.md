# Linux Studio compatibility and restart completion — 2026-11-24

## Initial frame and preserved baseline

Question: can a user start the actual extracted Studio package on a compatible Linux host, understand a CPU/library mismatch, and restart with workspace/history and the owned model intact? Architecture, CPU instruction support, dynamic ABI, persisted state, native model quality, hardware capacity, and deployment authority are separate acceptance dimensions. No combination of successful fixtures substitutes for a native model gate.

Baseline source `45225d1b4c07ace715fd8be9f7dcd994e659f598`, tree `ccf14867c8a1b3b4aa7cc96c23bdc338f9e2ebec`, already produced the accepted x86_64 package in [run 45483142281](https://github.com/Mannyspiro/expert-robot/actions/runs/45483142281). The previously delivered full ZIP and seven bounded delivery parts remain historical immutable outputs. This follow-up changes future packages; its new native acceptance is **pending until an exact-source matrix run completes**.

Observed gaps: the builder rejected non-x86_64 hosts; the native smoke started `server.py` directly rather than `START.sh`; CPU features and target ABI were not user-visible preflight gates. Inspection also found that saving the automatic model URL caused a restart to treat that endpoint as externally managed. The core integration repairs that ownership distinction; the new independent restart gate preserves this counterexample and requires actual model readiness after restart.

## Implemented release contract

`linux_preflight.check_linux_host(root, *, data_dir=None, probe_binary=False, verify_executables=False)` returns `merlin-linux-preflight/1`. The default reads bounded files only and returns architecture, ELF target, declared CPU requirements, and state-parent access observations. It does not spawn a process, activate a GPU, infer model readiness, or certify sufficient memory. The root resource API consumes this same report. The actual bundled-model launch boundary requests `verify_executables=True`, requiring both executable digests without creating an additional ABI subprocess. `probe_binary=True` always implies digest verification.

`START.sh --check` additionally verifies the native executable digests and invokes only `llama-server --version` with a clean environment, five-second deadline, and bounded output. This exercises the actual loader/ABI without loading model weights. It returns a nonzero status for incompatible native inputs. `OFFLINE_PLATFORM` is inventoried and must match the profile manifest; the shell checks it before attempting bundled Python. Normal startup preserves the offline workspace when only the optional inference engine is unavailable. `--headless` exercises the same launcher without starting a browser.

The builder uses separate ordinary Ubuntu matrix jobs for `linux-x86_64` and `linux-aarch64`. Both use the unchanged Qwen1.5B weights and llama source, matching pinned Python archives, CPU-only builds, disabled upstream UI modes, and two build/inference threads. `linux_build_requirements.py` rejects native host flags or actual CPU compile flags inconsistent with the declared baseline. This prevents ARMv9/SVE features on the runner from silently becoming requirements of an ARMv8-A package.

The unchanged arithmetic smoke must pass first, followed by the unchanged genuine-stream recorder. Then a separate fixed public workspace fixture is written through the actual API. CI shuts down and restarts the extracted `START.sh` with the same state directory, checks exact file/history hashes and completed-run persistence, and requires the actual model list after reload. The restart receipt cannot rescue an arithmetic or streaming failure. New bounded part artifacts are split only after all gates pass.

The clean runtime environment excludes credentials and disables Studio network tools. This is **not OS-enforced network isolation**; no host network namespaces, firewall policy, root permissions, or OCI settings are changed. Filesystem verification, launcher/API fixtures, and native runtime acceptance remain distinguishable evidence.

Independent review caught an initial launch-boundary defect: normal startup preserved the offline UI after a full preflight failure, but the later model launcher checked only static metadata. A same-architecture engine with changed bytes could therefore still be launched. The repair places mandatory digest verification inside `BundledModel.start`; its regression changes engine bytes while preserving a valid ELF header, proves static compatibility still passes, and asserts that no child is launched while the offline workspace stays ready. This is a local synthetic counterexample, not a claim that any accepted package's bytes were changed.
